## 1. Sung Jin Woo: «Arise» поднимает ВСЕХ мёртвых в радиусе 50 блоков

### Текущее поведение
<ref_snippet file="src/main/java/com/example/superheroes/ability/AriseAbility.java" lines="32-100" />

- Сейчас `Arise` ищет **одного** кандидата в радиусе `RANGE = 8.0`:
  - Сначала ближайший `DeathEcho` через `SungJinwooController.nearestDeathEcho(player, RANGE)` (TTL = 400 тиков = 20с, см. `SungJinwooController.DEATH_ECHO_TICKS`).
  - Если эхо нет — самый «слабый» живой моб (по `health/maxHealth`) в AABB.
- Спавнит **одну** тень на месте кандидата.
- `MAX_SHADOWS = 10` (общий лимит) — armies cap.
- Стоимость: 20 ENERGY, КД 40 тиков (2с).

### Что просит пользователь
> «фикс у сон жи ву чтоб из ВСЕХ мертвых в радиусе 50 блоков спавнились тени со способности ВОССТАНЬ. т.е вокруг персонажа радиус в 50 блоков и по способности вокруг него появляются все тени.»

То есть:
- Радиус **50 блоков** (вместо 8).
- Поднимает теней из **каждого** death-echo (а не только ближайшего).
- За один каст — одновременно несколько теней.

### Root cause
- `RANGE = 8.0` (константа в `AriseAbility`).
- `findCandidate` возвращает один `Candidate` — а нужно **список**.
- `MAX_SHADOWS = 10` ограничит «всех» — обсудить ниже.

### Предлагаемый фикс

**`AriseAbility`:**
1. `RANGE = 50.0` (константа).
2. Заменить `findCandidate(player) → @Nullable Candidate` на `findCandidates(player) → List<Candidate>`:
   - Собрать все валидные `DeathEcho` в радиусе (новый метод `SungJinwooController.collectDeathEchoes(player, RANGE)`).
   - Опционально: если живых echo меньше N — добирать «слабыми» живыми мобами (≤30% HP) до лимита, чтобы кнопка не была пустой при отсутствии трупов. **Дефолт = выкл, только trupy** (точно по заявке пользователя).
3. На активации — итерировать по списку, на каждой позиции звать `SungJinwooController.spawnOneShadowAt(...)` + `registerExtraShadow(...)`.
4. Спавн ограничить остатком слотов: `slots = MAX_SHADOWS - aliveCount(player)`. Если `candidates.size() > slots` — берём ближайшие (`Comparator.comparingDouble(c → player.position().distanceToSqr(c.pos()))`).

**Альтернатива по `MAX_SHADOWS`:**
- Оставить **10** как и сейчас → если у Сона уже 7 живых, Arise добавит максимум 3 даже если в радиусе 20 трупов. Это безопасно по балансу/перфу.
- Или поднять до 30 для героя phase2 (ult). Решает пользователь — спросить **перед реализацией**.

**FX/звук:**
- Сделать звук/частицы кратко в **каждой** точке + один общий «волну» из игрока (выбираем 1 `SoundEvents.WARDEN_EMERGE` + `ENDERMAN_TELEPORT` per location, частицы те же что сейчас).
- Чтобы не лагало при N=20+ — частиц на каждый спавн уменьшить до 20 SOUL_FIRE_FLAME + 30 PORTAL.

**Стоимость / КД:**
- Стоимость = `20 + 5 * (raised - 1)` ENERGY (масштабируется), либо фикс 20 если `raised >= 1`. Решение: оставить **20 фикс** (по заявке нет упоминания).
- КД оставить 40т (2с).

**`SungJinwooController` — новый метод:**
```java
public static List<Vec3> collectDeathEchoes(ServerPlayer player, double range) {
    ServerLevel level = player.serverLevel();
    List<DeathEcho> list = DEATH_ECHOES.get(level);
    if (list == null) return List.of();
    long now = level.getGameTime();
    Vec3 origin = player.position();
    double rSq = range * range;
    List<Vec3> result = new ArrayList<>();
    Iterator<DeathEcho> it = list.iterator();
    while (it.hasNext()) {
        DeathEcho e = it.next();
        if (e.expiresAt() <= now) { it.remove(); continue; }
        if (e.pos().distanceToSqr(origin) <= rSq) result.add(e.pos());
    }
    return result;
}

public static void consumeDeathEchoes(ServerPlayer player, Collection<Vec3> positions) {
    ServerLevel level = player.serverLevel();
    List<DeathEcho> list = DEATH_ECHOES.get(level);
    if (list == null) return;
    list.removeIf(e -> positions.contains(e.pos()));
}
```

### Поведение `consumeDeathEchoes`
Сейчас `consumeDeathEcho(player, pos)` удаляет один echo по позиции. Нужно расширить чтобы удалять все consumed positions.

### Сценарий «трупов 0, живых > 0»
По заявке нужно поднимать **только мёртвых**. Если в 50 блоках нет ни одного `DeathEcho` — `Arise` не активируется (ability returns false из `tryActivate`, ENERGY не списывается, сообщение «Нет тел в радиусе»). Текущий `canActivate` уже корректен — расширить до `!findCandidates(player).isEmpty()`.

### Scope / риск
- **M, med**. Риск перфоманса при больших раидах (50 блоков × все игроки) — нивелируется лимитом `slots`.

## 3. Регенерация не появляется у некоторых героев

### Текущее поведение
Permanent Regeneration в `applyPassives` имеют **только**:
- `SungJinwooHero.applyPassives` → `MobEffects.REGENERATION` lvl 0, duration -1
- `RegulusHero.applyPassives` → REGENERATION lvl 0, -1
- `DoomsdayHero.applyPassives` → REGENERATION lvl 1 / lvl 0 (зависит от tier)

**НЕ имеют permanent regen:**
- `HomelanderHero` — только `<20 HP` через `HomelanderRegenController` (gated).
- `IronManHero`, `GokuHero`, `NarutoHero`, `CaptainAmericaHero`, `SlendermanHero` — нет регенерации вообще.

### Что просит пользователь
> «пофиксить баг с регенерацией, у некоторых персонажей она почему то не появляется хотя должна быть.»

Два возможных диагноза:
- (A) Пользователь ожидает у героев, у кого её формально нет (Iron Man / Naruto / Cap / Goku / Slender) — это **фича**, а не баг.
- (B) У героев, где она должна быть (Sung / Regulus / Doomsday) — иногда **слетает**.

### Root cause для (B)
1. `HomelanderRegenController` в `tickPlayer` (CHECK_INTERVAL = 20) делает `player.removeEffect(MobEffects.REGENERATION)` всегда когда HP ≥ maxHP, **не проверяя что игрок именно Homelander**:
   <ref_snippet file="src/main/java/com/example/superheroes/effect/HomelanderRegenController.java" lines="55-67" />
   На самом деле гард `if (!isHomelander) { ACTIVE.remove(id); return; }` ЕСТЬ — это путь не задевает Sung/Regulus/Doomsday. Но! Гард пропускает только тех, у кого `ACTIVE.contains(id)` — а вообще это безопасно для Sung/Regulus.
   **Однако** есть ещё проблема: при смене героя (Homelander → Sung) `removePassives` Homelander-а не убирает REGENERATION (т.к. её ставит контроллер, не applyPassives), но `HomelanderRegenController` при следующем тике увидит `!isHomelander` и **уберёт REGENERATION** через `player.removeEffect(MobEffects.REGENERATION)` — даже если Sung только что её добавил. Race-condition.

2. `RegulusMadnessController` снимает REGENERATION при выходе из madness:
   <ref_snippet file="src/main/java/com/example/superheroes/effect/RegulusMadnessController.java" lines="265-285" />
   Если Regulus всегда имеет lvl 0 регенерации (через `applyPassives`), а в madness — lvl 4, то при выходе из madness `removeEffect(REGENERATION)` снимет ВСЁ → игрок остаётся без regen, до следующего respawn / re-transform.

3. `HeroTransformService.onPlayerJoin` / `onPlayerRespawn` ре-применяет passives — но если игрок уже в момент join имеет stale активный эффект (от vanilla load), `addEffect` с тем же типом может не override-нуть из-за amplifier-логики vanilla (`MobEffectInstance.update` смотрит amplifier и оставляет более сильный).

### Предлагаемый фикс
**Фикс A — race в `HomelanderRegenController`:**
- Сейчас контроллер при `!isHomelander` делает `ACTIVE.remove(id)` и `removeEffect(REGENERATION)` — переписать так, чтобы removeEffect происходил **только** если эффект был добавлен этим контроллером (флаг в `ACTIVE`):
  ```java
  if (!isHomelander) {
      if (ACTIVE.remove(id)) {
          // Снимаем регенерацию ТОЛЬКО если её ставил мы.
          player.removeEffect(MobEffects.REGENERATION);
      }
      return;
  }
  ```
  Уже так, **но** баг проявляется когда игрок был Homelander, попал в `ACTIVE`, потом сменил на Sung. На следующем tickInterval контроллер уберёт REGEN. Чинится через `if (!isHomelander)` ветку: **не вызывать `removeEffect`**, а просто очистить map (regen сейчас принадлежит новому герою). Если у Homelander-а правда нужно сразу убирать regen при смене — её должен убирать `HomelanderHero.removePassives`, а не контроллер.
  → Перенести `removeEffect` в `HomelanderHero.removePassives()` (он сейчас просто `HeroAttributes.HOMELANDER.remove(player)`):
  ```java
  @Override
  public void removePassives(Player player) {
      HeroAttributes.HOMELANDER.remove(player);
      player.removeEffect(MobEffects.FIRE_RESISTANCE);
      // Снимаем под-под-low-HP regen если активен
      if (player instanceof ServerPlayer sp) HomelanderRegenController.forceClear(sp);
  }
  ```

**Фикс B — Regulus madness exit стирает базовый regen:**
- В `RegulusMadnessController` после `removeEffect(REGENERATION)` явно перевыставлять базовый `RegulusHero.applyPassives`-эффект:
  ```java
  player.removeEffect(MobEffects.REGENERATION);
  // re-apply base passive regen (lvl 0, infinite)
  player.addEffect(new MobEffectInstance(MobEffects.REGENERATION, -1, 0, true, false, true));
  ```
  Или вместо `removeEffect` — заменить `addEffect(new ...lvl=0)` который автоматически override-нёт lvl=4 через `MobEffectInstance.update` после ManadnessAmplifier-effect-end.

**Фикс C — robust re-apply на join/respawn:**
- В `HeroTransformService.onPlayerJoin` и `onPlayerRespawn` перед `applyPassives` явно сделать `removeEffect` для всех permanent-эффектов героя (FIRE_RESISTANCE, REGENERATION) и затем re-add. Так гарантируется чистый стейт независимо от vanilla-NBT-restore:
  ```java
  if (data.hasHero()) {
      Hero hero = Heroes.get(data.heroId());
      if (hero != null) {
          // снимаем чтобы не было дублей с amplifier-конфликтом
          hero.removePassives(player);
          hero.applyPassives(player);
      }
  }
  ```

**Фикс D — добавить permanent regen героям, у кого она «должна быть» по лору:**
- Решение пользователя нужно (см. секцию A). Предложение по умолчанию (требует подтверждения):
  - Iron Man: НЕТ regen (костюм без авто-нанорепаира)
  - Naruto: lvl 0 regen (Курама заживляет) → **ДА**
  - Cap: lvl 0 regen (super-soldier serum) → **ДА**
  - Goku: lvl 0 regen (saiyan biology) → **ДА**, ускоренная вне боя.
  - Slenderman: НЕТ regen (он как фантом, не лечится)
  - Homelander: lvl 0 ALWAYS (вместо «<20HP») → **ДА**, и убрать `HomelanderRegenController` целиком.

  → отдельный PR/коммит после согласования.

## 4. Способности «отваливаются», лечится только полным рестартом

### Текущее поведение
- `AbilityCooldowns.MAP` хранит `Map<UUID, Map<ResourceLocation, Long>>` где значение — `deadline = player.tickCount + ticks`:
  <ref_snippet file="src/main/java/com/example/superheroes/ability/AbilityCooldowns.java" lines="18-37" />
- `EnergyLocks.LOCKS`: аналогично, `deadline = player.tickCount + ticks`.
- `EyeLasersAbility.PULSE_TICK`: `Map<UUID, Integer>` — пульс-фаза.
- `CapShieldSlamAbility.JUMPING`: `WeakHashMap<UUID, Integer>` — счётчик air-time.

### Root cause
**Главный баг:** `player.tickCount` — это **per-Entity** счётчик, который **resetится в 0 при создании ServerPlayer** (т.е. на каждый respawn / dimension change / relog ServerPlayer создаётся заново и `tickCount = 0`).

Сценарий:
1. Игрок использует ability, `tickCount = 5000`, КД 200 → `deadline = 5200`.
2. Игрок умирает, respawn → новый `ServerPlayer`, `tickCount = 0`.
3. UUID игрока тот же. `MAP.get(uuid).get(ability) == 5200`.
4. `isOnCooldown` сравнивает `0 < 5200` → возвращает true.
5. Способность залочена на 5200 тиков (4.3 минуты) — пока tickCount не догонит.
6. Если игрок умирает чаще чем раз в 4 минуты — способность **навсегда залочена**.
7. Полный рестарт сервера обнуляет `MAP` (статическое поле) → способность снова работает.

То же самое: `EnergyLocks.LOCKS`, `PULSE_TICK` (если ability был активен на момент смерти, можно остаться с устаревшей фазой), `JUMPING` (не критично, WeakHashMap).

### Предлагаемый фикс

**Фикс A — перевести deadlines на server-wide gametime:**
В `AbilityCooldowns`:
```java
public static void setCooldownTicks(ServerPlayer player, ResourceLocation abilityId, int ticks) {
    long deadline = player.serverLevel().getGameTime() + ticks;
    MAP.computeIfAbsent(player.getUUID(), k -> new ConcurrentHashMap<>())
            .put(abilityId, deadline);
    ServerPlayNetworking.send(player, new AbilityCooldownS2CPayload(abilityId, ticks));
}

public static boolean isOnCooldown(ServerPlayer player, ResourceLocation abilityId) {
    Map<ResourceLocation, Long> m = MAP.get(player.getUUID());
    if (m == null) return false;
    Long deadline = m.get(abilityId);
    if (deadline == null) return false;
    long now = player.serverLevel().getGameTime();
    if (now >= deadline) {
        m.remove(abilityId);
        return false;
    }
    return true;
}
```
То же — в `remainingTicks`. Аналогично — `EnergyLocks`.

`level.getGameTime()` монотонно растёт всё время пока сервер запущен (включая dimension change / respawn / relog).

**Фикс B — очистка стейтов при respawn / disconnect:**
- В `HeroTransformService.onPlayerRespawn(newPlayer)` сбросить активные toggle-флаги в `HeroData`:
  ```java
  HeroData data = newPlayer.getAttachedOrCreate(ModAttachments.HERO_DATA);
  if (data.hasHero()) {
      // Очистить activeAbilities — после смерти все toggle off
      HeroData cleared = data.clearActive();
      newPlayer.setAttached(ModAttachments.HERO_DATA, cleared);
      Hero hero = Heroes.get(cleared.heroId());
      if (hero != null) {
          hero.removePassives(newPlayer); // safety
          hero.applyPassives(newPlayer);
      }
  }
  ModNetworking.syncHeroData(newPlayer, data);
  ```
- В `ServerPlayConnectionEvents.DISCONNECT` (новый hook в `SuperheroesMod`) — очистка `AbilityCooldowns.clear(uuid)`, `EnergyLocks.clear(uuid)` (новый метод), `EyeLasersAbility.PULSE_TICK.remove(uuid)`, `FlightController.ACTIVE_SINCE.remove(uuid)`, и т.д. Все pure-RAM мапы.

  Альтернатива (предпочтительная): вынести clear в **общий метод** `ClientStateRegistry.onDisconnect(uuid)` который дёргает все controllers сразу. Но проще сделать поштучно (≤10 мест).

**Фикс C — гарантировать deactivate всех toggle на смерть:**
- В `ServerLivingEntityEvents.AFTER_DEATH` для `ServerPlayer` пробежаться по `data.activeAbilities()` и вызвать `AbilityRouter.deactivate(player, id)`. Это очистит side-effects (например, FlightController.ACTIVE_SINCE).

**Фикс D — `HeroData.copyOnDeath` сейчас копирует `activeAbilities`** — что неправильно, после смерти все toggle должны быть выключены. Решение:

  Если API не поддерживает map-on-copy — использовать вариант с onPlayerRespawn.

## 10. Слендермен: модель смотрит в одну сторону, не поворачивается

### Что было
В плане v3.0-user-fixes.md (§1) предложен фикс через `prevBodyYaw` + `setYHeadRot` + skip render в FIRST_PERSON. PR #50 заявил «Slenderman cloak: синхронизация yaw/head yaw, интерполяция поворота и скрытие cloak-модели в first-person». Однако пользователь говорит:
> «пофиксить НОРМАЛЬНО ПОВОРОТ МОДЕЛЬКИ СЛЕНДЕРА. все еще он просто смотрит в 1 сторону и не поворачивается в стороны.»

Т.е. фикс в PR #50 не дотянул.

### Текущий код
<ref_snippet file="src/main/java/com/example/superheroes/effect/SlendermanCloakController.java" lines="100-125" />

`controller` каждый тик ставит:
```java
cloak.moveTo(nowPos.x, nowPos.y, nowPos.z, yaw, 0f);
cloak.setYRot(yaw);
cloak.setYHeadRot(yaw);
cloak.setBodyYaw(yaw);
```

### Root cause (новые гипотезы после v3.0)
1. **`Entity.moveTo(...)` сбрасывает `yRotO = yRot`** — т.е. интерполяция между тиками всегда «прыгает» сразу к новому значению, GeckoLib читает `yRot` без интерполяции с предыдущим тиком, **но** для не-LivingEntity нет `yBodyRot`/`yBodyRotO`. Поэтому `setYHeadRot` ничего не делает (это поле есть только у LivingEntity).
2. **GeckoLib `GeoEntityRenderer<Entity>`** для не-LivingEntity по умолчанию НЕ применяет `Mth.rotLerp(partialTick, entity.yRotO, entity.getYRot())` так как делает это только при `tickCount > 0` — нужно явно проверить.
3. **Наследование от `Entity` (а не `LivingEntity`)** — это корень. `LivingEntity` имеет `yBodyRot`, `yBodyRotO`, `yHeadRot`, `yHeadRotO` — без них GeckoLib не интерполирует body отдельно от head.
4. **Network packet truncation** — сервер шлёт `ClientboundMoveEntityPacket` с rotation как `byte` (256 шагов). При большой смене yaw за 1 тик > 180° vanilla truncate-ит до короткой стороны — выглядит как рывок.

### Предлагаемый фикс

**Главный шаг: переделать `SlendermanCloakEntity` extends `Mob` (не `Entity`)**:
- `Mob` extends `LivingEntity`. Получаем поля `yBodyRot`/`yBodyRotO`/`yHeadRot`/`yHeadRotO` бесплатно.
- Делаем `noPhysics = true`, `setNoAi(true)`, `setInvulnerable(true)`, `setSilent(true)`, `setNoGravity(true)`.
- Размер entity 0.0×0.0 (невидимая hitbox), чтобы не блокировала ходьбу игрока.
- Нужен `RegistryEntries.entityType` с `MobCategory.MISC` + `EntityType.Builder.of(SlendermanCloakEntity::new, MobCategory.MISC).noSummon().noSave().sized(0f, 0f).build()`.

**Контроллер:**
```java
float yaw = slender.yBodyRot;
cloak.setPos(nowPos.x, nowPos.y, nowPos.z); // не moveTo — moveTo сбрасывает rotO
cloak.yBodyRotO = cloak.yBodyRot;
cloak.yBodyRot = yaw;
cloak.yHeadRotO = cloak.yHeadRot;
cloak.yHeadRot = yaw;
cloak.yRotO = cloak.getYRot();
cloak.setYRot(yaw);
cloak.xRotO = cloak.getXRot();
cloak.setXRot(0f);
```
Если за тик угол меняется > 180° — нормализовать через `Mth.degreesDifference(prev, target)` чтобы интерполяция шла короткой стороной.

**Renderer:**
- В `SlendermanCloakRenderer extends GeoEntityRenderer<SlendermanCloakEntity>` — переопределить `preRender`/`actuallyRender` чтобы:
  ```java
  poseStack.mulPose(Axis.YP.rotationDegrees(180f - Mth.rotLerp(partialTick, entity.yBodyRotO, entity.yBodyRot)));
  ```
  если базовый GeoEntityRenderer этого не делает для нашего случая.

**1-st person hide (уже было — проверить что работает):**
- В `SlendermanCloakRenderer.shouldRender` — early return если камера == owner cloak-а И `CameraType.FIRST_PERSON`.
- Также `addRenderLayers(...)` — пропустить layers для self-cloak в 1-st person.

**Альтернатива — render через mixin `LivingEntityRenderer`:**
Вместо отдельного entity, использовать `HeroSkinLayer`-аналог для слендера — рендерим GeoModel поверх player-renderer-а как layer. Тогда yaw — это `player.yBodyRot`, никаких отдельных entity не нужно.

Этот вариант **проще и стабильнее** — рекомендуется.

Минусы:
- Player-skin под GeoModel будет виден в просветах между body parts. Решение — либо геометрия cloak-а плотная (закрывает skin полностью), либо использовать `AbstractClientPlayerSkinMixin` чтобы скрыть ваниль-скин при `isSlenderman` (как это делают для Homelander/Iron Man).

## 11. Vibranium Shield: своя модель, не vanilla

### Текущее поведение
- `VibraniumShieldItem extends ShieldItem` — наследует vanilla shield-логику (блок, durability, sound, animation).
- Модель собрана из 7 layered-textures (`vibranium_shield/0..5,1_2`) на одной 1×12×12 plane через сложный JSON. Это даёт нестандартный вид.
- Проектайл `ShieldProjectileEntity` использует тот же ItemStack + анимация рендера.

### Что просит пользователь
> «бля забудь про эту модельку щита. нарисуй сам модельку и используй ее.»

То есть: отказаться от текущей слоёной модели и сделать **геометрию щита через JSON-cuboid-ы** (или через GeoModel).

### Предлагаемый фикс

**Подход 1: чистая JSON-cuboid модель (рекомендуется)**

1. Новая `models/item/vibranium_shield.json`:
   - Использует `parent: minecraft:item/handheld` (чтобы рука держала).
   - Геометрия — circular shield (диск 14×14 пикселей × 1 пиксель толщины) собранный из 4–6 cuboid-плиток с разными faces-uv.
   - Текстуры — 1 PNG `textures/item/vibranium_shield_face.png` (256×256 face artwork: круг с белой звездой, красно-белые кольца, синий центр) + опц. `vibranium_shield_back.png`.
   - `display`: настройки для `firstperson_righthand`, `thirdperson_righthand`, `gui` (как у vanilla shield).
2. Удалить старую слоёную модель + 8 текстур (`vibranium_shield/0..5,1_2,vibranium`).
3. Добавить новую текстуру: `textures/item/vibranium_shield_face.png` (256×256).
   - Рисуем сами через утилиту (Python PIL / ImageMagick) или текстура из `art-source/`. Если в `art-source/` есть готовая (`marvel/cap-shield-*.png`) — взять её, конвертировать в 64×64 или 256×256 PNG.
   - Пользователь явно сказал «нарисуй сам» — значит сгенерировать программно. Простая колор-схема: red ring (#C8242A), white ring, red ring, blue center с белой 5-конечной звездой.
4. `models/item/vibranium_shield_projectile.json` — отдельная модель для projectile (более «плоская», без рук-pose).

**Подход 2: GeoModel (через GeckoLib) — overkill, не рекомендуется**

Использовать GeckoLib для кастомного 3D-щита с возможностью анимаций. Но:
- Vanilla `ShieldItem` не интегрирован с GeckoLib renderer.
- Придётся отказаться от наследования `ShieldItem` и сделать `Item` + custom `BuiltInItemRenderer` через `BuiltinModelItemRenderer` (Fabric provides API).
- Большая работа, **только если пользователь хочет анимированный щит**.

**Декомпозиция (подход 1):**
1. Сгенерировать новую текстуру `vibranium_shield_face.png` 256×256 (Python скрипт или вручную) — соответствие классическому Cap-shield.
2. Заменить `models/item/vibranium_shield.json` — простая «диск из 4 кубоидов».
3. Заменить `models/item/vibranium_shield_projectile.json` — то же, но без `display.firstperson_*`.
4. Удалить лишние слой-текстуры `vibranium_shield/0..5, 1_2, vibranium`.
5. `VibraniumShieldItem` — оставить наследование от `ShieldItem` (vanilla animation block работает).
6. `ShieldProjectileEntity.render` — без изменений, использует ItemStack.
7. Если проблема в том, что vanilla shield-анимация не подходит — заменить наследование на просто `Item` + ручную имплементацию `use()`/`releaseUsing()` для блока. Уточнить у пользователя.

### Затронутые файлы
- `src/main/resources/assets/superheroes/models/item/vibranium_shield.json` (заменить)
- `src/main/resources/assets/superheroes/models/item/vibranium_shield_projectile.json` (заменить)
- `src/main/resources/assets/superheroes/textures/item/vibranium_shield_face.png` (новый)
- удалить `textures/item/vibranium_shield/{0..5,1_2,vibranium}.png` (8 файлов)
- (опц.) `src/main/java/com/example/superheroes/item/VibraniumShieldItem.java` — если меняем суперкласс.
